# ADR-017 — Typed API contract: request/response records, RFC 9457 errors, generated OpenAPI and TypeScript types; paths stay unversioned

- **Status:** `APPROVED` — decided by the product owner in the portfolio-upgrade brief of 12/11/2026 (typed records with Bean Validation, ProblemDetail, committed OpenAPI, generated TS types, **no `/api/v1`**).
- **Summary (EN):** Every endpoint now takes and returns typed records instead of `Map<String, Object>`/`JsonBody`; the hand-written `RawInput` parser became a typed `PlanningInput`. Errors are `application/problem+json` (RFC 9457) with a stable `code`. The OpenAPI document is generated by the application, committed as `backend/openapi.yaml` and checked for staleness by a test; the web client's types are generated from it. API paths are deliberately not versioned.
- **Related:** ADR-003 (layers, CQRS), ADR-005 (bearer sessions), [`docs/architecture/api-contract.md`](../api-contract.md).

## Context

Before this change the controllers read the body as a raw JSON map (`JsonBody`) and the application layer parsed it by hand (`RawInput`, 342 lines), and returned `Map.of("trip", view)`. That preserved two product rules exactly (a missing key is different from `null`; an amount is a number or a string of digits, never guessed), but there was no machine-readable contract, no generated documentation, errors in an ad-hoc shape, and nothing stopped a controller from taking a `Map` again.

## Decision

1. **Typed request and response records per module** (`<module>/api/request`, `<module>/api/response`). Controllers use `@RequestBody` records and return response records; commands carry typed values, not maps. An ArchUnit rule (`API-1`) fails the build if a controller method takes or returns a `Map` or a `JsonBody`; `JsonBody`, its argument resolver and `RawInput` are deleted.
2. **"Not sent / null / value" is modelled explicitly** with `Patch<T>` (already used in the domain), read by a Jackson 3 deserializer (`PatchDeserializer`: absent key → `Patch.absent()`, JSON `null` → `Patch.of(null)`). No Jackson-2-only library (such as `jackson-databind-nullable`) is added. Amounts and durations that may be a number *or* a digit string use `FlexibleNumber`.
3. **Strict JSON types.** Scalar coercion is off (a string is not accepted for a number, nor a number for a string, nor `4.5` for an integer), except the documented leniency that `""` where a list is expected is an empty list (web forms send it).
4. **Where validation lives.** Jackson enforces JSON types; a wrong type is reported as the error the request record declares for that field (`@InputError`, default `MALFORMED`). Bean Validation (`@NotNull`, `@Size`…) covers shape constraints that are independent of loaded state and maps to the existing codes (`REQUIRED`, `TOO_LONG`, `TOO_MANY`, `OUT_OF_RANGE`). Format and business rules (D17 amounts, dates, vocabularies) stay in the application/domain, applied **after the aggregate is loaded**, so errors keep the documented order (for example a deleted item is `ITEM_DELETED` before any field error). Domain invariants never move to the API layer.
5. **Errors are RFC 9457 problem details** (`application/problem+json; charset=UTF-8`): `type` (`urn:wander:problem:<code>`), `title`, `status`, `detail` (user-facing message), `instance`, plus the extensions `code` (stable, what the web client switches on), optional `field` and `details`. The 401 entry point uses the same shape.
6. **The OpenAPI 3.1 document is generated by the running application** (springdoc), served at `/v3/api-docs` (Swagger UI at `/swagger-ui`) everywhere except the `free` profile, and **committed** as `backend/openapi.yaml`. `OpenApiContractIT` fails the build if the file is stale; regenerate with `make gen-api`. The web's `contract.generated.ts` is generated from the committed file (`openapi-typescript`) and CI fails if it differs; the client uses it to prove at compile time that the field names it sends and reads exist in the contract.
7. **Paths are not versioned (no `/api/v1`).** The only client is the single-page app that ships in the same Docker image as the API, so a breaking change is deployed together with the client that needs it; the Render service, the keep-warm ping, the e2e suite and the web client all use the current paths. Versioning would add a URL scheme and a compatibility matrix with no consumer to benefit. When a second independent client or a public consumer appears, add the new version side by side (`/api/v2/...`) and keep the old one until it is unused.

## Intentional differences from the hand-written parser

These are consequences of typed requests, accepted on purpose:

- A value of the wrong **JSON type** (for example `"cover": "x"`, `"title": 5`) is rejected while the body is read, with `400`, **before** the trip is loaded or the caller is authorized. Well-typed but invalid values keep the old order.
- Where the old code silently ignored a wrong-typed optional value (checklist `group`/`title`, `position`, `skipRecoveryCode`), it is now `MALFORMED`.
- `evidence` of the wrong type when regenerating the recovery code is `400 MALFORMED` instead of `403 STEP_UP_REQUIRED`; both reject.
- Error bodies changed shape (top-level `code`, `detail` instead of `error.message`) and content type.
- Responses gained the standard `instance` member (the request path the caller sent).

## Consequences

- The contract is documented, browsable and testable; the generated web types caught a real inconsistency on first use (the client could send `cover` when creating a trip, which the API never read).
- More files (about 30 request/response records and 4 holder classes), in exchange for typed commands and no `Object` parsing.
- Strict typing changes some error codes for malformed input; those are listed above and pinned by tests.
